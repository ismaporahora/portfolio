Um bug de UX que vinha do modelo de dados

Função
Product Designer — diagnóstico, proposta, implementação de frontend
Período
Junho de 2026 (deploy em 17 de junho)
Ferramentas
Claude Code · gravações de sessão · feedback de usuários
O problema O diagnóstico A proposta A correção Ressalva
Em resumo — As professoras viam suas turmas duplicadas na interface. A causa não era um bug de UI: o modelo de dados exigia uma disciplina (materia) na criação da turma, então uma mesma turma do mundo real virava vários objetos no sistema. Propus desacoplar a disciplina da turma, e a correção foi para produção em 17 de junho.

O problema

Na escola primária argentina, do ponto de vista da professora, não existem disciplinas: existem turmas. O produto pedia uma disciplina ao criar uma turma. Uma professora que dava aulas de Língua (Lengua) e de Matemática para uma única turma de 3º ano acabava com duas turmas “3º ano” na lista dela. Na interface, parecia uma duplicação. No modelo de dados, estava funcionando como projetado.

O diagnóstico

Os relatos do bug apontavam para a lista de turmas. As gravações de sessão e o modelo de dados apontavam para outro lugar: o acoplamento da disciplina à turma no momento da criação. Corrigir a lista teria escondido o sintoma.

A proposta

Escrita no formato problema / proposta / considerações / decisão, o mesmo que uso em toda proposta de produto (um exemplo anterior: o redesign de janeiro para gerar planos sem uma turma criada). A proposta: o formulário da turma deixa de pedir a disciplina (e a quantidade de alunos); a disciplina passa a ser pedida na hora de planejar, toda vez.

A correção

Foi para produção em 17 de junho de 2026. Agora cada grupo do mundo real corresponde a uma única turma. A disciplina fica onde a professora realmente pensa nela: na hora de planejar.

Ressalva

RessalvaDesde a correção, o número de turmas criadas ainda é pequeno demais para dizer se a confusão com turmas duplicadas desapareceu. Este caso é o diagnóstico, não o resultado.
